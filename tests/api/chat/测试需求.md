# Chat 接口测试需求

## 测试范围

**仅测试 `POST /api/chat/completions` 接口**。

不测试的内容：
- 对话 CRUD
- 消息查询
- `newConversation=true`（有逻辑但不测）
- 图片超过 5 张 / 链接超过 5 个的 400 校验
- 取消聊天（UI 上没有取消按钮）

## 业务逻辑梳理

### 对话路由（API 层 `completions.ts`）

```
传入 conversationId?
  ├─ 是 → 使用该 conversationId
  └─ 否 → 传入 newConversation?
            ├─ 是 → 创建新对话
            └─ 否 → getLatest()
                    ├─ 有 → 复用最新对话
                    └─ 无 → 创建新对话
```

### ChatGraph 执行流程（7 节点线性）

```
Init → SaveMemory → RecognizeImage → FetchUrl → Search → StreamLLM → Finalize
```

- **Init**: 获取模型/KB/Agent，加载历史消息（过滤已记忆），构建 langchainMessages
- **SaveMemory**: 未记忆消息 token 累计超过阈值时，调用 KB 写入记忆并标记 memoried
- **RecognizeImage**: 有图片且模型不支持 vision 时，用 vision 模型识图
- **FetchUrl**: 有 urls 时，抓取链接内容
- **Search**: LLM 判断是否需要联网搜索/记忆搜索，执行搜索并构建 systemPrompt
- **StreamLLM**: 流式调用 LLM，逐 chunk 推送，计算 token 倒减
- **Finalize**: 保存 assistant 消息，推送 done 事件（含 token 计数）

### Regenerate 逻辑

1. API 层校验：消息必须存在且未记忆（memoried=false），否则 400
2. `removeMessagesAfter(convId, regenerateMessageId)`：删除该消息**之后**的所有消息（不删自身）
3. 不添加新 user 消息，直接用历史消息进 LLM 重新生成 assistant 回复
4. 重发后对话中该 user 消息仍在，其后的旧 assistant 回复已删除，新回复已写入

### Processing 互斥

同一 conversationId 正在处理时（Redis key `chat:processing:{convId}`），再次请求返回 400。

## 测试策略

### 核心原则

1. **只测 `POST /api/chat/completions`**，不测其他接口
2. **顺序执行**：`describe.sequential`，利用前序用例创建的数据
3. **只在 `beforeAll` 清空一次数据库**：后续用例利用已有数据
4. **SDK 调用方式**：`chat()` 返回 `conversationId`，`consume(onEvent)` 消费流事件获取 `ChatResult`

### 执行顺序与数据依赖

```
beforeAll: cleanupConversations() → 清空数据库，获取 kbId / modelId

━━━ 一、对话路由 ━━━
用例1: 空库聊天 → 自动创建新对话，保存 convId1
用例2: 有对话时复用最新 → convId === convId1
用例3: 传已有 conversationId → 在指定对话中继续聊天

━━━ 二、参数校验 ━━━
用例4: 缺少 modelId → 400
用例5: 缺少 kbId → 400
用例6: 缺少 messages → 400

━━━ 三、Processing 互斥 ━━━
用例7: 同一对话正在处理时再次请求 → 400

━━━ 四、流事件序列 ━━━
用例8: 首 token 时间 ≤ 10s
用例9: 流事件序列 chunk → done（含 token 计数）
用例10: 流事件包含 messageId（user + assistant）
用例11: 流事件包含 status 事件

━━━ 五、消息持久化 ━━━
用例12: 聊天完成后消息正确保存

━━━ 六、Regenerate ━━━
用例13: 重发消息 → 删除后续消息并重新生成
用例14: 重发后继续聊天 → 新消息追加在重发生成的内容之后

afterAll: client.disconnect()
```

## 测试用例

### 一、对话路由

| # | 用例 | 说明 | 断言 |
|---|------|------|------|
| 1 | 空库时聊天 — 自动创建新对话 | `beforeAll` 已清空数据库，不传 `conversationId` | `conversationId` 非空 + `fullContent` 非空 + `userTokens > 0` + `completionTokens > 0` + `totalTokens > 0` + `listConversations().total === 1` 且 ID 匹配 |
| 2 | 有对话时复用最新对话 | 不传 `conversationId`，数据库已有用例 1 的对话 | `conversationId === convId1` |
| 3 | 传已有 conversationId 继续聊天 | 传 `conversationId: convId1` | `conversationId === convId1` + `fullContent` 非空 |

### 二、参数校验（400）

| # | 用例 | 说明 | 断言 |
|---|------|------|------|
| 4 | 缺少 `modelId` | `modelId` 为空 | HTTP 400 |
| 5 | 缺少 `kbId` | `kbId` 为空 | HTTP 400 |
| 6 | 缺少 `messages` | 请求体无 `messages` 字段 | HTTP 400 |

### 三、Processing 互斥

| # | 用例 | 说明 | 断言 |
|---|------|------|------|
| 7 | 同一对话正在处理时再次请求 → 400 | 发起 chat → 不等完成 → 立即对同一 conversationId 再发 chat | 第二次请求返回 400 "上一次消息尚未处理完成" |

### 四、流事件序列

| # | 用例 | 说明 | 断言 |
|---|------|------|------|
| 8 | 首 token 时间 ≤ 10s | 从发起请求到收到第一个 chunk 事件的时间 | `firstChunkTime > 0` + `ttfb ≤ 10000ms` |
| 9 | 流事件包含 `chunk → done` 序列（含 token 计数） | 收集所有事件验证顺序 | `indexOf('chunk') < indexOf('done')` + done 事件 `userTokens > 0` + `completionTokens > 0` |
| 10 | 流事件包含 messageId（user + assistant） | 至少包含 `role=user` 和 `role=assistant` 的 messageId | `messageIdEvents.length >= 2` + 存在 user 和 assistant 两种 role |
| 11 | 流事件包含 status 事件 | 验证聊天流程中推送了状态通知 | `statusEvents.length >= 1` + status 值为 StreamStatus 枚举中的合法值 |

### 五、消息持久化

| # | 用例 | 说明 | 断言 |
|---|------|------|------|
| 12 | 聊天完成后消息正确保存 | 聊天完成后 `getMessages(convId1)` | 包含 `role=user` 和 `role=assistant` 的消息 + assistant 消息 content 非空 + user 消息 tokens > 0 |

### 六、Regenerate

| # | 用例 | 说明 | 断言 |
|---|------|------|------|
| 13 | 重发消息 — 删除后续消息并重新生成 | 获取对话中最后一条 assistant 消息 ID，传 `regenerateMessageId` 聊天 | 新 assistant 消息 content 与之前不同 + 该 assistant 消息之后的消息已被删除（消息总数 = 之前总数 - 1 + 1） |
| 14 | 重发后继续聊天 — 新消息追加在重发内容之后 | 在用例 13 的对话中继续发新消息 | `conversationId === convId1` + `fullContent` 非空 + `getMessages()` 中新 user 消息在重发生成的 assistant 消息之后 |

## 实现要点

- **单文件**：所有用例在 `completions.test.ts` 中
- **`describe.sequential`**：保证用例按书写顺序执行
- **`vitest.config.ts` 设置 `fileParallelism: false`**：防止文件间并行
- **SDK 调用方式**：
  ```typescript
  const conversationId = await client.chat({ messages, modelId, kbId })
  const result = await client.consume((event) => { /* 收集事件 */ })
  // result: ChatResult { conversationId, fullContent, error, userTokens, ... }
  ```
- **用例 7 的 processing 互斥实现**：`chat()` 返回后 LLM 仍在处理，立即对同一 conversationId 发第二次请求，断言 400
- **用例 13 的 regenerate 实现**：
  1. 先 `getMessages(convId1)` 获取最后一条 assistant 消息的 ID 和 content
  2. 调用 `chat({ conversationId: convId1, regenerateMessageId: lastAssistantMsg.id, modelId, kbId, messages: [] })`
  3. consume 流事件等待完成
  4. 再次 `getMessages(convId1)` 验证新的 assistant 回复与之前不同
- **用例 14 的重发后继续聊天**：在用例 13 的基础上，正常发一条新消息，验证消息顺序正确
